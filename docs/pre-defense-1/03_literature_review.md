# 03 — Literature Review

> Sources: 19 peer-reviewed scientific publications (9 from 2021–2026), 1 scholarly book, 1 ISO standard and primary technical documentation. Full verified bibliography: [references.md](references.md). Each record's metadata was checked against Crossref on 2026-10-20.
> **Depth of reading:** for S15–S19 the summaries below rely on the published abstracts (publisher, ACL Anthology or arXiv pages). For S1–S14 they reflect the papers' well-known published contributions. Where a summary is abstract-level, the table says so. 

## 1. Review questions

- **RQ1.** How do existing approaches generate residential layouts and building models from high-level requirements?
- **RQ2.** How are building models represented and validated (BIM objects, rules, geometric consistency)?
- **RQ3.** What is known about using LLMs to turn natural language into building designs, and what are their limitations?
- **RQ4.** What human-AI interaction principles apply to a design assistant?

Search strategy: Crossref and publisher sites (ACM DL, IEEE Xplore, ScienceDirect, ASCE Library, ACL Anthology, MDPI), arXiv for preprint versions, and ISO for standards. Keywords: *floor plan generation, residential layout generation, procedural modeling buildings, rule-based model checking BIM, LLM BIM generation, text-to-floorplan, generative AI architectural design review, human-AI interaction guidelines, structured output LLM*. Inclusion: peer-reviewed, directly relevant to RQ1–RQ4, verifiable DOI. Recent work (2021–2026) was preferred, with older foundational papers kept where later work builds on them.

## 3. Critical synthesis

### 3.1 What is already known

1. **Layouts can be generated from high-level requirements.** Two lines of work exist. Optimization and procedural methods use explicit rules and objectives [S1–S3]. Data-driven generators learn from large plan datasets [S6–S10]. The learned methods now produce vector plans that respect geometric relations [S10] and support iterative refinement [S9].
2. **Language is a viable but hard interface.** Tell2Design shows that NL → floor plan is far from solved because designs carry hard spatial and relational constraints [S11]. Recent LLM systems therefore do **not** let the LLM produce the layout alone. They add rule-based checkers, planners and separate geometry executors [S18, S19].
3. **Object-based models make validation possible.** Rule checking works when the model has typed objects and the rules are in machine-interpretable form [S4]. Rule complexity varies a lot, and derived-geometry rules are the expensive class [S5]. IFC is the open standard for exchanging such models [T1, B1].
4. **AI tools need to explain themselves.** Human-AI guidelines stress communicating capability and uncertainty, explaining behavior and supporting correction [S14].

### 3.2 Existing approaches and their limitations (relative to BuildAI's goal)

| Approach family | Typical output | Limitation for an element-level, verifiable residential model |
|---|---|---|
| Procedural grammars [S1] | 3D shells/facades | No interior program; expert grammar authoring |
| Stochastic optimization [S2, S3] | Plans + simple 3D | Not reproducible without seeding; no formal validation |
| Learned generators [S6–S10] | 2D room boxes / vector plans | No walls/openings/slabs/roofs as typed objects; hard constraints not guaranteed; dataset-bound |
| Text → plan datasets/models [S11] | 2D plans | Gap to human quality; constraint satisfaction remains open |
| LLM writes BIM code [S18] | Editable BIM in an authoring tool | Geometry produced by LLM-generated code needs iterative checking; tied to one tool |
| LLM multi-agent + diffusion [S19] | 2D layouts | Geometry still from a learned model; output is a layout, not a building model |

Methodological gaps: reviews report that evaluation is mostly comparative or subjective [S16], and that LLM adoption in AECO is held back by integration and reliability [S17]. Structured output may itself cost reasoning accuracy [S15], which few design papers measure.

### 3.3 What BuildAI 3D reuses

- **Explicit rules and scoring** for layout [S2, S3]. BuildAI uses a seeded candidate search with scoring, so results are reproducible.
- **Procedural, rule-driven geometry** [S1], applied to typed elements with panel decomposition instead of CSG.
- **Separating rule checking from the model** and reporting findings with references [S4]. Classifying checks by complexity guides what the model must store versus derive [S5].
- **A user-editable intermediate representation** [S7, S8]. BuildAI's intermediate is a typed `BuildingSpecification` rather than a graph, editable through a form.
- **Human-AI guidelines** [S14]: clarification questions, a requested-vs-generated summary, listed assumptions and the provider shown in the UI.

### 3.4 What BuildAI investigates differently

1. **The AI produces intent only.** Unlike Text2BIM, where the LLM writes code that creates the model [S18], and diffusion-based geometry in [S19], BuildAI's LLM outputs only a schema-validated `BuildingSpecification`. A deterministic engine creates all geometry. **Research question for the evaluation:** does this separation keep 100 % geometric validity while keeping interpretation accuracy comparable to direct approaches?
2. **Element-level output, not 2D layouts.** The output is a typed model (walls, hosted openings, slabs, stairs, roofs) with a geometric-constraint catalog (37 constraints on `main`). That is a building model, not a picture or a plan raster [contrast S6–S11].
3. **Objective, reproducible evaluation.** Determinism (same input ⇒ same model), validation pass rates and interpretation accuracy against expected spec facts. This answers the reviews' criticism that evaluation is mostly subjective [S16].
4. **Format-restriction trade-off measured in a design domain.** BuildAI already has two output modes (strict JSON Schema and a schema-in-prompt fallback). Comparing them on the same prompts tests the concern raised in [S15] in a building-design setting.
5. **Honest scope.** Conceptual, residential, rectilinear, ≤ 3 storeys. The platform doesn't claim code compliance, unlike tools aimed at professional delivery.

### 3.5 Threats to the validity of this review

- 19 papers is a focused rather than systematic sample. The thesis should extend the search (e.g. Scopus or Web of Science queries with documented counts).
- Several 2025–2026 summaries are abstract-level (marked in the table).
- Commercial tools are covered in [04](04_existing_system_comparison.md) from vendor claims, not peer-reviewed evidence.
