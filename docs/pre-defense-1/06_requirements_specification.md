# 06 — Requirements Specification

> Status values: **Implemented** = merged on `main` and covered by automated tests that passed on (web 135 / API 582 passed, 2 skipped) and/or recorded browser verification · **Implemented (branch)** = committed on `phase-3.5-k3-design-systems`, not merged and not re-tested in this sprint · **Partial** · **Planned**.
> Verification methods: **T** automated test (file named) · **D** demonstration in the browser (screenshot in `assets/screenshots/`) · **I** inspection of code/config · **E** experiment (see [09](09_verification_and_evaluation_plan.md)).
> Priorities (MoSCoW) are the team's current judgement. They are revisited after the user interviews ([02](02_relevance_and_user_evidence.md)).
> Test paths are relative to `apps/api/tests/` (API) or `apps/web/src/` (web).

## 1. Functional requirements

| ID | Description | Priority | Rationale | Acceptance criteria (testable) | Verification | Status |
|---|---|---|---|---|---|---|
| FR-01 | The user can describe a building in natural language | Must | Core interaction; lowers the expertise barrier | A prompt of 3–`AI_MAX_PROMPT_CHARS` (default 4000) characters is accepted; longer prompts are rejected with a validation error; `Ctrl+Enter` submits | T `ai/test_generation_api.py::test_configured_prompt_limit_is_enforced`; D screenshot 03 | Implemented |
| FR-02 | The system turns the description into a validated `BuildingSpecification` | Must | The AI produces intent only (CLAUDE.md rule 2) | Provider output is accepted only if it passes Pydantic, `rules.spec_checks` and the form-field checks; invalid output gets ≤ `AI_MAX_REPAIRS` (default 1) repair calls and is never accepted | T `ai/test_interpreter.py` (accept, repair once, fail after one repair) | Implemented |
| FR-03 | The system asks clarification questions when a request is too vague | Should | Avoids inventing a program; human-AI guideline on uncertainty [S14] | A vague prompt (e.g. "I want a nice house.") returns a clarification outcome with ≥ 1 question and no version is created; answers are understood on the next attempt | T `ai/test_generation_api.py::test_vague_prompt_asks_for_clarification`, `ai/test_mock_provider.py`; D screenshot 12 | Implemented |
| FR-04 | The user can enter or edit a structured specification (size, floors, rooms, style, garage, seed) | Must | Precise control without AI; works offline | The form produces a valid spec 1.0.0; reference presets load; "Check specification" shows issues with JSON-pointer paths | T `generation/components/SpecForm.test.tsx`; D screenshot 10 | Implemented |
| FR-05 | Specifications are validated against the active rules profile | Must | Dimensions come only from rules profiles (rule 16) | Out-of-range values return issues carrying `rule_ref` and a JSON pointer; nothing is generated from an invalid spec | T `rules/test_spec_checks.py`, `test_versions_generation_api.py` | Implemented |
| FR-06 | The system generates a building layout deterministically from a valid spec | Must | Core engine; reproducibility | For each of the 10 reference specs: model is produced, `validate_model` has 0 errors, no `ROOM_UNREACHABLE`, no rules findings, GFA within ±3 % of request; golden files match | T `layout/test_reference_specs.py`, `layout/test_invariants.py` (Hypothesis) | Implemented (`layout@1.2.0`) |
| FR-07 | Generated models contain typed elements: walls, rooms, doors, windows, slabs, stairs, roofs, railings, furniture | Must | Element-level model (rule 3) | Every element has id, type, name, layer, level_id, position, rotation, dimensions, material_id, properties, relationships, origin, locked, semantic_key; schema validation passes | T `building/test_validation.py`, `building/test_schema_export.py` | Implemented |
| FR-08 | The user can view the model in interactive 3D | Must | Visual evaluation of concepts | Orbit/zoom/pan, 7 camera presets + reset, perspective/orthographic; model renders from the stored version | T `engine/scene/*.test.ts`; D screenshots 01, 05 | Implemented |
| FR-09 | The user can select an element and inspect its properties | Must | Element-level transparency | Clicking a mesh or room selects exactly one model element and shows dimensions, material, placement, properties, relationships (e.g. "Hosted by"), identity (UUID, semantic key) | T `engine/scene/selection.test.ts`, `editor/components/PropertiesPanel.test.tsx`; D screenshot 06 | Implemented |
| FR-10 | The user can isolate floors, toggle layers, hide roof/exterior walls/furniture and use a section cut | Should | Interior inspection | "Floor 2" shows only floor 2 (lower floors ghosted); layer toggles hide the matching elements | T `engine/scene/visibility.test.ts`; D screenshot 07 | Implemented |
| FR-11 | The system shows requested-vs-generated facts, warnings, assumptions and engine notes | Must | Trust and explainability [S14] | After generation the summary lists floors, area, bedrooms, bathrooms, balconies, garage (requested → generated, ✓/deviation), warnings (count), assumptions (list); the report adds deviations, geometry checks and the rules check | T `ai/components/GenerationSummary.test.tsx`, `versions/components/ReportPanel.test.tsx`; D screenshots 05, 08 | Implemented |
| FR-12 | Doors and windows are hosted by walls with host-relative placement | Must | Geometric consistency; BIM-like hosting | Every opening has exactly one `hosted_by` wall on the same level, lies within the wall's length and height, and never overlaps another opening; violations produce `HOST_*` / `OPENING_*` findings | T `building/test_geometry_checks.py` (host tests), `layout/test_geometry_constraints.py` | Implemented |
| FR-13 | The system validates geometry and reports machine-readable findings | Must | Validity by construction + verification | 37 cataloged constraints; each finding carries `constraint`, `code`, `severity`, `related_ids`, `measure`; findings are deterministic; catalog and docs stay in sync (test) | T `building/test_geometry_checks.py::test_findings_are_deterministic`, `layout/test_geometry_constraints.py` | Implemented (K2.5) |
| FR-14 | The user can request appearance and color preferences (e.g. "yellow facade") | Should | Expressive intent at concept stage | Spec 1.1.0 `design.facade_color` (palette name or `#rrggbb`) colors every exterior wall face; material unchanged; invalid colors rejected (`APPEARANCE_INVALID`) | T (branch) `building/test_design_intent.py`, `layout/test_design_layout.py`; E live call recorded in branch roadmap | Implemented (branch), not merged |
| FR-15 | The user can request directional facade/window preferences (e.g. panoramic windows to the garden, standard to the street) | Should | Common brief element | Preferred facades are glazed first; excluded facades get standard windows only; conflicts produce `WINDOW_FACADE_CONFLICT` / `WINDOW_PREFERENCE_UNSATISFIABLE`, never silently changed; rooms can face front/rear | T (branch) `layout/test_design_layout.py`, `ai/test_design_intent_api.py` | Implemented (branch), not merged |
| FR-16 | Each generation creates a new immutable project version | Must | Reproducibility; rule 11 | Generating twice gives v1, v2; earlier versions are unchanged and can be selected; each version stores spec, seed, rules profile, engine version, provenance | T `test_versions_generation_api.py::test_generate_creates_a_version`; D screenshot 11 | Implemented |
| FR-17 | The system keeps a generation history per project | Should | Traceability | History lists prompt, status, provider, duration, linked version; stored in `ai_generations` / `ai_runs` | T `ai/test_generation_api.py`; D screenshot 09 | Implemented |
| FR-18 | The operator can configure the AI provider and model by environment only | Must | Vendor neutrality (rule 13) | `AI_PROVIDER ∈ {mock, anthropic, openrouter}`; missing key/model fails fast at startup; unknown provider rejected; model name never in business logic; production refuses `mock` | T `ai/test_provider_selection.py`, `test_config.py` | Implemented |
| FR-19 | Failures are reported with distinct codes and user-safe messages | Must | Usability and security | Provider errors, invalid output, infeasible layouts and rate limits map to distinct error codes in the `{error:{code,message,details}}` envelope; no stack traces or secrets in responses | T `ai/test_generation_api.py`, `ai/test_openrouter_provider.py`, `test_auth.py::test_register_validation_error_has_json_pointer_paths` | Implemented |
| FR-20 | Users authenticate and can access only their own projects | Must | Security | Unauthenticated requests → 401; another user's project → 404; applies to projects, versions, generation, AI tools | T `test_projects.py`, `ai/test_generation_api.py::test_ownership_is_enforced`, `test_versions_generation_api.py::test_generation_requires_auth_and_ownership` | Implemented |
| FR-21 | Guests can view the hand-authored demo house without logging in | Could | Demo / onboarding | `/` renders the demo model served by `GET /api/v1/demo/building-model` (validated before serving) | T `test_demo_api.py`; D screenshot 01 | Implemented |
| FR-22 | Compare and restore versions | Should | Design iteration | Element diff coloring + fact deltas; restore creates a new version | E | Planned (Phase 5) |
| FR-23 | Modify a design in natural language through typed operations | Should | Core product vision | "Make the kitchen 2 m wider" → `ModificationPlan` → preview diff → new version | E | Planned (Phase 5) |
| FR-24 | Quantities and preliminary cost (KZT, demo catalog) | Could (for diploma) | Product vision | Hand-verified quantities within 1 % on the fixture house; estimate labelled preliminary/demo | E | Planned (Phase 4) |
| FR-25 | Export report / IFC | Could | Interoperability [T1] | PDF report per version; IFC export validated by an IFC viewer | E | Planned (backlog) |

## 2. Non-functional requirements

| ID | Category | Description | Priority | Rationale | Acceptance criteria | Verification | Status |
|---|---|---|---|---|---|---|---|
| NFR-D1 | Determinism | Same spec + seed + rules profile + engine version ⇒ byte-identical model | Must | Reproducible research results; rule 5 | Repeated generation gives identical model JSON, also under two different `PYTHONHASHSEED`s; golden geometry fingerprints unchanged unless deliberately updated | T `layout/test_engine.py::test_determinism_does_not_depend_on_hash_seed`, golden files | Implemented |
| NFR-D2 | Determinism (viewer) | Same model ⇒ identical scene/geometry | Must | Rule 20 | Scene hash for the demo and generated fixtures matches the stored value | T `engine/scene/generated-model.test.ts`, `build-scene.test.ts` | Implemented |
| NFR-C1 | Contracts | One schema source: Pydantic → JSON Schema → TS types + Zod | Must | Prevents client/server drift | Committed generated schemas equal freshly generated ones (test) | T `building/test_schema_export.py`, `ai/test_provider_selection.py::test_committed_ai_json_schema_is_up_to_date` | Implemented |
| NFR-S1 | Security — auth | Short-lived JWT access tokens (15 min default) + rotating, hashed refresh tokens in an httpOnly cookie; argon2id password hashing | Must | Industry practice | Refresh rotates; reuse of an old refresh token revokes the token family; logout revokes | T `test_auth.py::test_refresh_rotates_token`, `::test_refresh_token_reuse_revokes_family`, `test_security.py` | Implemented |
| NFR-S2 | Security — secrets/config | No secrets in the repository; production refuses unsafe settings | Must | — | `.env` is git-ignored; `JWT_SECRET` ≥ 32 chars; production rejects placeholder secret, insecure cookie and the mock provider | T `test_config.py`; I `.gitignore` | Implemented |
| NFR-S3 | Security — abuse | Per-user AI rate limit and one active generation per project | Must | Cost control | > `AI_GENERATIONS_PER_HOUR` (default 30) requests → rate-limit error; a second concurrent generation is refused | T `ai/test_generation_api.py::test_rate_limit` | Implemented |
| NFR-S4 | Security — prompt injection | User text is quoted as data in prompts; AI output is untrusted until validated | Must | LLM risk | Prompt modules quote user input; validation pipeline as in FR-02 | T `ai/test_prompts.py`; I `ai/prompts/` | Implemented |
| NFR-S5 | Security review | An independent security review before any public deployment | Should | Hand-written auth | Review checklist completed, findings fixed | I | Planned (Phase 8) |
| NFR-R1 | Reliability | Interrupted jobs or generations are marked failed on startup, never left running | Should | Consistent state | Restart marks in-progress jobs failed | T `test_versions_generation_api.py::test_interrupted_jobs_are_failed_on_startup`, `ai/test_generation_api.py::test_interrupted_generations_are_failed_on_startup` | Implemented |
| NFR-P1 | Performance — viewer | A 2-storey generated house renders interactively | Should | Usability | Scene build < 200 ms and ≥ 30 fps orbiting for the 280 m² reference house on the dev laptop | D (status line shows build 39–40 ms, 144 meshes, ~7k triangles: screenshots 05–06); fps **not yet measured** | Partial |
| NFR-P2 | Performance — generation | End-to-end generation latency is bounded and reported | Should | Usability, evaluation | Mock provider: < 5 s end-to-end; live LLM: median and p95 reported per stage; timeout `AI_TIMEOUT_SECONDS` (default 120 s) enforced | D history shows "mock interpreter · 1.3 s" (screenshot 09, one observation); E for live LLM | Partial (live latency not measured) |
| NFR-U1 | Usability | A first-time user can generate and inspect a building without instructions | Should | Target users are non-experts | ≥ 4/5 participants complete "describe → generate → isolate floor 2 → inspect a window" unaided; SUS ≥ 68 | E (usability session) | Planned |
| NFR-U2 | Transparency | Every view that shows results shows the conceptual-use disclaimer | Must | Rule 18; liability | Disclaimer visible in footer, report and rules panels | I `app/core/disclaimer.py`, web `DISCLAIMER`; D all screenshots (footer) | Implemented |
| NFR-E1 | Extensibility — elements | A new element type needs only a schema class, a builder registration and tests | Should | Maintainability | Documented procedure in `docs/3d-engine.md`; registry-based builders | I `engine/builders/registry.ts` | Implemented |
| NFR-E2 | Extensibility — providers | A new LLM provider is one adapter module; vendor SDKs are imported only there | Must | Rule 13 | import-linter contract "Vendor AI SDKs are imported only by their provider adapter" kept | T `pnpm lint` (import-linter 5/5 contracts kept, 2026-10-20) | Implemented |
| NFR-M1 | Maintainability — domain purity | Domain modules don't import FastAPI, SQLAlchemy, DB or AI | Must | Testability; rule 6 | import-linter contracts kept; mypy strict passes | T `pnpm lint`, `pnpm typecheck` (clean on 2026-10-20) | Implemented |
| NFR-M2 | Portability | Runs on Windows dev machines without Docker; Docker Compose for full stack | Should | Team environment | `pnpm db:local` + `pnpm dev` work on Windows; `docker compose up --build` brings up db/api/web | D Windows ✔ (this sprint); Docker **not verified** (no Docker on the dev machine) | Partial |
| NFR-M3 | Backward compatibility | Stored models are upgraded on read and never rewritten | Must | Immutable versions | 1.0.0 fixtures load as current schema; stored rows/hashes unchanged | T `building/test_migrations.py` | Implemented |
